# 2 技术理论基础

本章针对医院检查数据管理平台的开发过程中所涉及的相关技术与理论基础进行介绍，依次对后端架构技术、前端框架、核心算法理论和医疗数据合规规范进行了说明，为后续系统的需求分析、设计与实现提供理论支撑。

## 2.1 后端架构相关技术

### 2.1.1 Spring Boot 后端开发框架

Spring Boot 是由 Pivotal 团队在 Spring Framework 基础上推出的一款轻量级 Java 开发框架，其核心理念是"约定优于配置"（Convention over Configuration）。在传统的 Spring 项目开发中，开发者需要编写大量的 XML 配置文件来管理 Bean 的依赖注入、事务配置、数据源定义等基础设施，项目搭建阶段的工作量大且容易出错。Spring Boot 通过自动配置（Auto-Configuration）和起步依赖（Starter Dependency）两大机制解决了这一问题——自动配置会根据 classpath 中引入的 JAR 包自动推测并装配所需的 Bean，起步依赖则将一组功能相关的依赖打包为单一坐标，开发者只需引入一个 starter 即可获得整套技术栈的依赖传递。

与传统的 WAR 包部署模式不同，Spring Boot 内嵌了 Tomcat、Jetty 等 Servlet 容器，应用可以打包为可独立运行的 JAR 文件，通过 `java -jar` 命令直接启动，无需额外配置外部应用服务器。这一特性大幅简化了部署流程，特别适合需要快速上线、独立运行的科室级轻量应用场景。在版本方面，Spring Boot 3.x 系列全面支持 JDK 17 的现代语法特性（如 Record 类、文本块、模式匹配等），并在底层升级到 Jakarta EE 9+ 的命名空间，提供了更好的运行时性能和安全性。

本系统在构建后端服务时采用了 Spring Boot 3.2.5 版本，利用其自动配置能力集成了 MyBatis-Plus、Redis、WebSocket 等技术组件；利用其内嵌容器实现了"一个 JAR 包即可运行"的轻量化部署；利用其 `@Scheduled` 注解驱动定时任务引擎；利用其 `@Aspect` 注解支持面向切面编程，实现了操作日志的声明式拦截。

### 2.1.2 MyBatis-Plus 数据持久化技术

在 Java 生态中，对象关系映射（Object-Relational Mapping, ORM）框架承担着将关系型数据库中的表记录与 Java 对象相互转换的关键职责。MyBatis 是这一领域的一款半自动 ORM 框架，与 Hibernate 等全自动框架不同，MyBatis 不强制使用全映射策略，而是允许开发者通过 XML 映射文件或注解的方式手写 SQL 语句，在保持数据库操作灵活性的同时避免了框架自动生成 SQL 带来的性能不确定性。

MyBatis-Plus 是在 MyBatis 基础上由苞米豆团队开发的增强工具，其核心设计原则是"只做增强不做改变"——在完全兼容 MyBatis 所有功能的前提下，提供了通用 CRUD 接口（BaseMapper）、条件构造器（QueryWrapper 和 LambdaQueryWrapper）、分页插件（PaginationInnerInterceptor）和代码生成器等开箱即用的扩展能力。以条件构造器为例，开发者无需为每种查询条件组合编写独立的 SQL 语句，而是通过链式调用 `.eq()`、`.like()`、`.between()` 等方法动态构建 WHERE 子句，框架在运行时根据实际传入的非空参数自动生成对应的 SQL，这使得多条件组合查询场景下的代码量大幅减少。

分页是数据管理系统中最常用的功能之一。MyBatis-Plus 的分页插件通过拦截器机制对 SQL 执行过程进行增强：在原始查询 SQL 执行之前，插件自动追加数据库方言对应的分页语句（如 MySQL 的 `LIMIT offset, size`），同时执行一条 `COUNT(*)` 查询获取总记录数，将分页数据和总条数一并封装返回。这种无侵入的方式使得开发者只需传入分页参数对象即可获得完整的分页结果，无需在每处查询中重复编写分页逻辑。

本系统在数据访问层采用了 MyBatis-Plus 3.5.5 版本。对于大部分单表的增删改查和条件筛选操作，利用 BaseMapper 的内置方法和 QueryWrapper 动态拼接即可完成；对于跨多张表的联合查询和统计聚合等复杂场景，则通过自定义 XML 映射文件手写 SQL 实现。

### 2.1.3 MySQL 关系型数据库

MySQL 是目前 Web 应用开发中使用最为广泛的开源关系型数据库管理系统之一，由瑞典 MySQL AB 公司开发，后被 Oracle 公司收购。作为一款关系型数据库，MySQL 将数据以"表-行-列"的二维结构进行组织，通过主键和外键约束来维护实体之间的关联关系，支持 SQL（Structured Query Language）标准语法进行数据的定义、查询、更新和控制。

MySQL 具备以下几项核心特性：支持 InnoDB、MyISAM 等多种存储引擎，其中 InnoDB 支持行级锁、事务（ACID）和外键约束，是 OLTP（联机事务处理）场景的事实标准引擎；提供 B-Tree 索引、哈希索引和全文索引等多种索引结构，通过合理的索引设计可显著降低查询的磁盘 I/O 次数；支持主从复制和组复制等高可用方案，为数据容灾和读写分离提供基础能力。在版本迭代上，MySQL 8.0 引入了窗口函数、通用表表达式（CTE）、JSON 原生支持等新特性，在性能和功能上较 5.x 版本有了显著提升。

本系统采用 MySQL 8.0 作为后端关系型数据库，负责存储患者基本信息、四类检查记录、检验结果、医嘱数据、用户权限和操作日志等全部结构化业务数据。

### 2.1.4 Redis 缓存中间件

Redis（Remote Dictionary Server）是一款开源的、基于内存的键值对（Key-Value）存储系统。与传统的关系型数据库将数据存储在磁盘上不同，Redis 将所有数据保存在内存中，使得读写操作可以达到微秒级延迟，单节点实例的吞吐量通常超过每秒十万次操作。为了在服务器重启后不丢失数据，Redis 提供了 RDB（定时快照）和 AOF（追加日志）两种持久化策略，二者可独立或组合使用。

在数据结构方面，Redis 不仅支持简单的 String 类型，还内置了哈希（Hash）、列表（List）、集合（Set）、有序集合（Sorted Set / ZSet）、位图（Bitmap）等多种高级数据结构，每种数据结构均有对应的原子操作命令。例如，ZSet 类型通过为每个成员关联一个 double 类型的分数，可在 O(log N) 时间内实现成员的排序插入和范围查询，适合用于实现滑动窗口限流、排行榜和延迟队列等场景。在部署模式上，Redis 支持单节点、主从复制、哨兵模式和集群模式，可根据业务规模灵活选择。

本系统引入 Redis 作为热点数据的缓存中间件：将检验项目字典、参考范围等高频读取但低频变更的基础数据缓存到内存中，减少数据库的重复查询压力；利用其高效读写能力缓存孤立森林模型的 Z-Score 统计参数，加速异常检测的评分计算。

### 2.1.5 JWT 认证

JWT（JSON Web Token）是一种基于 JSON 格式的开放标准（RFC 7519），用于在通信双方之间以紧凑且自包含的方式传递声明（Claim）信息。一个完整的 JWT 由三部分组成：头部（Header）、载荷（Payload）和签名（Signature），三部分以点号（`.`）分隔后进行 Base64URL 编码，形成形如 `xxxxx.yyyyy.zzzzz` 的字符串。

头部通常包含两个字段：令牌类型（`typ`，固定为 JWT）和签名算法（`alg`，如 HMAC-SHA256 或 RSA）。载荷则包含一组称为 Claims 的键值对，分为已注册声明（如 `iss` 签发者、`exp` 过期时间、`sub` 主题）、公共声明和私有声明三类，开发者可在私有声明中自定义业务字段。签名部分由头部和载荷的 Base64URL 编码拼接后，使用头部声明的算法和密钥进行加密计算得到，用于验证令牌在传输过程中是否被篡改。

JWT 最大的特点是无状态性：令牌本身已经包含了身份验证所需的所有信息，服务端无需维护会话状态或查询数据库即可完成身份校验，这使得 JWT 特别适用于前后端分离和分布式架构。在实际使用中，客户端将 JWT 存储在浏览器本地（如 localStorage），后续每次请求通过 HTTP 请求头的 `Authorization: Bearer <token>` 字段携带令牌，服务端拦截器提取令牌后验证签名和有效期即可确认用户身份。

本系统采用 JWT 作为前后端分离架构下的无状态用户认证方案，用户登录成功后后端签发包含用户 ID 和登录账号的 Token，后续请求通过拦截器统一校验 Token 的有效性。

### 2.1.6 RBAC 权限控制模型

RBAC（Role-Based Access Control，基于角色的访问控制）是由美国国家标准与技术研究院（NIST）提出的一种广泛应用于企业级系统的权限管理模型。其核心思想是在用户和权限之间引入"角色"这一中间抽象层：系统管理员将一组操作权限授予某个角色，再将角色分配给用户，用户通过扮演该角色间接获得相应的权限集合。这种三层间接关联的设计，使得在拥有大量用户和大量权限的系统中，管理员无需为每个用户逐一配置权限，只需维护"角色-权限"的对应关系即可管理所有用户的访问能力。

RBAC 模型包含五个基本元素：用户（User）、角色（Role）、权限（Permission）、会话（Session）和约束（Constraint）。其中约束条件可定义互斥角色（同一用户不能同时拥有两个互斥角色）、角色基数限制（一个角色最多分配给 N 个用户）和前提角色（拥有角色 A 是获得角色 B 的前提）等规则，进一步增强权限管理的安全性。

一个完整的 RBAC 权限校验流程通常包含三个步骤：用户登录认证成功后，系统查询该用户所关联的全部角色；遍历所有角色，汇总各角色对应的全部权限，合并为当前用户的权限集合；在每次执行业务操作前，检查该操作对应的权限编码是否存在于用户的权限集合中，存在则放行，否则拒绝。相比直接在代码中硬编码权限判断逻辑（如 `if user.role == "admin"`），RBAC 模型将权限关系数据化，支持在运行时动态调整角色-权限的对应关系而不需要修改代码。

本系统基于 RBAC 模型设计了"用户-角色-权限"三级权限体系，实现了对患者管理、检查记录管理、检验结果管理等全部业务操作的细粒度授权。

### 2.1.7 EasyExcel 数据导入导出技术

在 Java 生态中，操作 Excel 文件的传统方案主要有 Apache POI 和 JXL。Apache POI 提供了全面的 Office 文件读写能力，但其核心机制是将整个 Excel 工作簿（Workbook）的全部数据一次性加载到内存中构建对象树。对于中小规模文件（数百至数千行），这种模式运行正常；但当需要处理数万条甚至数十万条数据时，全量加载的方式会导致内存占用急剧膨胀，极易触发 OutOfMemoryError，导致服务不可用。

EasyExcel 是阿里巴巴开源的一款针对大文件 Excel 操作的轻量级工具库，其核心优化策略是摒弃了 Apache POI 的全量加载模式，改为基于 SAX（Simple API for XML）的逐行解析方式。在文件读取时，EasyExcel 将 xlsx 文件底层的 XML 数据流逐行解析为 Java 对象，每解析完一行即回调用户的监听器（ReadListener）进行处理，处理完毕后该行对象即可被垃圾回收器回收，不再保留在内存中。在文件写入时，EasyExcel 同样采用逐行写入的策略，将数据分批刷新到磁盘，避免大量数据堆积在内存中。得益于这种流式处理机制，EasyExcel 能够以极低的内存开销（通常在 MB 级别）处理百万行级别的 Excel 文件。

EasyExcel 通过注解驱动的映射机制简化了 Java 对象与 Excel 列的对应关系。开发者在 POJO 类的字段上标注 `@ExcelProperty` 注解并指定列索引或列名，框架即可在读取时自动将 Excel 单元格的值注入字段，在写入时自动将字段值填入对应列。这一设计使得数据导入导出的代码从数百行的手工解析简化为数行的注解声明和 API 调用。

本系统在历史数据批量导入和统计报表导出功能中使用了 EasyExcel，以流式处理的方式完成了数万条 Excel 记录的迁移与输出。

### 2.1.8 规则引擎 Easy Rules

在传统的业务系统开发中，大量的业务规则（如"当检验结果值超过阈值上限 1.5 倍时标记为危急""当用户连续三次登录失败时锁定账号 30 分钟"等）通常以 if-else 语句的形式散落在业务代码中。当规则数量较少时，这种方式尚可维护；但随着规则不断累加，分散在各处的条件判断语句会形成互相缠绕的逻辑网络，修改一条规则可能需要同时改动多个类，测试和排错的成本显著上升。

规则引擎（Rule Engine）正是为解决这一问题而设计的一种软件组件，其核心设计理念是将业务规则从应用程序代码中分离出来，以声明式的方式单独定义和管理。当一个业务事件发生时，引擎根据预先加载的规则集自动完成条件匹配和执行动作，业务代码只需关注"触发规则引擎"这一动作本身，而不需要了解每条规则的具体逻辑。这种分离带来了三个主要优势：规则可以在不修改代码、不重新部署的情况下动态调整；业务逻辑的意图在规则定义层面一目了然；新增和删除规则不会影响其他规则的执行。

Easy Rules 是 Java 平台上一款轻量级的规则引擎框架，API 简洁且不依赖外部组件。一个 Easy Rules 规则由三个核心要素构成：Facts（事实）是规则作用的数据对象，携带了规则判断所需的各项属性；Conditions（条件）定义了规则触发的判断逻辑，当事实中的属性值满足条件时，规则被激活；Actions（动作）则是在条件满足后执行的操作集合。Easy Rules 支持四种规则定义方式：通过注解声明、通过流式 API 编程式构建、通过 MVEL 表达式语言定义，以及通过 RuleDescriptor 描述符组装，开发者可根据场景灵活选择。

本系统在预警模块中引入 Easy Rules，将检验指标的阈值告警规则以数据记录的形式存储于数据库中，实现规则的动态配置与运行时加载。

### 2.1.9 Spring Task 定时任务框架

定时任务是后端系统中一项基础而常用的能力——数据备份需要每天凌晨定时执行，过期日志需要每周定时清理，统计数据需要每小时定时重新计算。在 Java 生态中，实现定时任务有多种方案：操作系统层面的 crontab（Unix/Linux）或 Task Scheduler（Windows）、独立的调度框架如 Quartz 和 Elastic-Job，以及 Spring 框架内置的 Spring Task。

Spring Task 是 Spring 框架原生的定时任务模块，无需额外引入第三方依赖。其使用方式极其简洁：在 Spring Boot 启动类上添加 `@EnableScheduling` 注解开启定时任务功能，然后在任意 Spring Bean 的方法上添加 `@Scheduled` 注解并配置触发规则即可。`@Scheduled` 支持三种触发策略：`fixedRate`（以固定频率执行，以上一次任务开始时间为基准计时）、`fixedDelay`（以上一次任务结束时间为基准间隔指定时间后执行）和 `cron`（使用 Cron 表达式精确指定执行时刻，如"0 0 2 * * ?"表示每日凌晨 2:00）。其中 Cron 表达式是一种由空格分隔的六位或七位字符串，依次表示秒、分、时、日、月、周（和年），能够灵活表达各种周期性时间规则。

Spring Task 的执行机制是基于线程池的单线程调度——所有标注了 `@Scheduled` 的任务默认在同一个线程池中排队执行，如果某个任务执行时间过长会阻塞后续任务。开发者可通过配置自定义线程池大小来支持任务的并行执行。对于大多数中小规模应用的非关键性定时任务（如数据备份、统计计算），Spring Task 在功能覆盖度和使用便捷性上达到了很好的平衡。

本系统利用 Spring Task 实现了数据库定时自动备份、预警规则周期性扫描和孤立森林模型的定期重训练等后台任务。

## 2.2 前端技术介绍

### 2.2.1 Vue.js 框架

Vue.js 是一套由尤雨溪开发的渐进式前端框架，采用 MVVM（Model-View-ViewModel）架构模式，以数据驱动和组件化开发为核心设计理念。与 Angular 这种"全家桶"式的一站式框架不同，Vue.js 的"渐进式"特征意味着其核心库仅聚焦于视图层的渲染与状态管理，开发者可按需逐步引入路由（Vue Router）、状态管理（Vuex / Pinia）、构建工具（Vite）等周边生态组件，从简单的页面交互逐层扩展到复杂的单页应用（SPA, Single Page Application）。

Vue.js 的响应式系统是其最核心的特性。当一个普通的 JavaScript 对象被传入 Vue 实例的 `data` 选项中时，Vue 使用 `Object.defineProperty`（Vue 2.x）或 Proxy（Vue 3.x）拦截该对象所有属性的读取和赋值操作。当模板中使用了某个数据属性（读取），Vue 将该属性注册为一个"依赖"；当该属性被修改时（赋值），Vue 自动通知所有依赖该属性的 DOM 节点重新渲染。这种"数据变、视图自动变"的机制将前端开发人员的关注点从手动操作 DOM 中解放出来，开发者只需关心数据的状态变更，框架负责将数据映射到视图。

在组件化方面，Vue.js 将页面拆分为独立可复用的 `.vue` 单文件组件，每个组件包含 `<template>`（HTML 模板）、`<script>`（JavaScript 逻辑）和 `<style>`（CSS 样式）三个部分，组件之间通过 props 向下传递数据、通过事件向上传递消息，形成了清晰的数据流向。

本系统前端采用 Vue.js 2.6 版本，基于其组件化模式将患者管理、检查录入、统计分析等页面拆分为独立组件，通过双向数据绑定实现了表单数据与展示视图的实时同步。

### 2.2.2 Element UI 组件库

Element UI 是饿了么前端团队推出的一套基于 Vue.js 2.x 的桌面端 UI 组件库，提供了表单（el-form）、表格（el-table）、弹窗（el-dialog）、日期选择器（el-date-picker）、树形控件（el-tree）、分页器（el-pagination）等数十种经过精心设计的常用组件。每个组件均经过大量的实际业务场景验证，交互行为稳定、视觉效果统一，能够显著降低企业级后台管理系统的界面开发成本。

Element UI 的组件采用声明式配置模式：开发者通过在 HTML 模板中添加对应的 Element 标签并配置属性（props）来控制组件的外观和行为，通过监听组件暴露的事件（events）来响应用户的操作。例如，表格组件支持通过 `data` 属性绑定数据源、通过 `columns` 数组定义列配置和格式化函数、通过 `@row-click` 事件监听行点击行为。这种配置驱动的开发方式使得开发者无需关心 DOM 结构的拼接和样式的微调，只需关注业务数据本身。

本系统使用 Element UI 搭建了用户界面，利用其表单、表格、弹窗和导航组件实现了信息录入、数据列表展示、操作确认和菜单导航等交互功能。

### 2.2.3 ECharts 可视化库

ECharts 是由百度开源的一款基于 JavaScript 的数据可视化图表库，底层依赖轻量级的 Canvas 类库 ZRender 进行渲染。ECharts 提供了折线图、柱状图、饼图、散点图、雷达图、热力图、仪表盘等二十余种常用图表类型，支持图例筛选、数据区域缩放、tooltip 悬浮提示、图表联动等丰富的交互操作，同时内置了数据转换、视觉映射和动画过渡等功能组件。

在图表配置方面，ECharts 采用 `option` 对象声明式配置模式：一个完整的 option 定义了图表的标题（title）、图例（legend）、提示框（tooltip）、X 轴（xAxis）、Y 轴（yAxis）和系列数据（series）等要素。开发者只需构建好 option 对象并调用 `echarts.setOption(option)` 即可完成图表的渲染，当数据更新时再次调用同一方法，ECharts 会通过数据比对自动执行动画过渡。

在性能方面，ECharts 对于万级数据点采用了采样策略和增量渲染技术，在保证可视化效果的前提下将渲染帧率维持在交互可接受的范围内。在大数据量模式下（如超过十万个数据点），可通过配置 `large: true` 和 `largeThreshold` 参数启用渐进式渲染，跳过一部分数据点的绘制以保持图表的流畅性。

本系统使用 ECharts 实现了检验指标历史趋势折线图、科室工作量的月度柱状图、检查类型占比的环形饼图以及医生工作量排名的可视化展示。

### 2.2.4 WebSocket 通信协议

在 Web 应用的实时通信场景中，传统的 HTTP 协议采用"请求-响应"模式，即客户端主动发起请求、服务器被动返回响应，服务器无法主动向客户端推送数据。为了实现服务端推送，早期 Web 应用中常采用轮询（Polling）和长轮询（Long Polling）两种折中方案：轮询是指客户端以固定频率不断发送查询请求，无论服务器是否有新数据，都会消耗网络和服务器资源；长轮询则让服务器在有数据时再响应，但仍然需要客户端每次主动发起连接。

WebSocket 是由 IETF 标准化的全双工通信协议（RFC 6455），它通过在客户端和服务器之间建立一个持久的 TCP 连接，使得双方可以随时、双向地发送数据，无需反复建立和断开连接。一次 WebSocket 会话的生命周期分为三个阶段：握手阶段，客户端发送一个携带特殊头信息（`Upgrade: websocket` 和 `Connection: Upgrade`）的 HTTP 请求，服务端理解该请求后返回 101 状态码（Switching Protocols），双方将通信协议从 HTTP 升级至 WebSocket；数据传输阶段，建立了持久连接后，客户端和服务器均可随时通过 `send()` 方法发送数据帧，数据以帧（Frame）为单位进行传输，每个帧可以是文本帧或二进制帧，不同帧之间由协议自动完成分片和重组；关闭阶段，任意一方发送关闭帧即可结束连接。

本系统在预警模块中使用 WebSocket 实现了预警消息的实时推送——当后台扫描到异常检验结果时，通过建立的 WebSocket 连接将预警消息主动推送到在线医护人员的浏览器。

## 2.3 核心算法理论

### 2.3.1 Z-Score 标准化算法

在医疗检验数据分析场景中，一个基础性的问题在于不同检验指标之间的量纲和量级差异巨大。例如，白细胞计数的正常范围通常在 4.0~10.0 × 10⁹/L 之间，数值变动通常在个位数级别；而碱性磷酸酶的正常范围在 45~125 U/L，部分异常值可达数百甚至上千。如果直接将原始检验值输入异常检测模型，量级大的指标会在距离计算中主导结果，量级小的指标几乎不产生影响，导致分析结论失真。

Z-Score（标准分数，也称为 Z 值或标准正态偏差）是统计学中一种常用的数据标准化方法，用于衡量单个数据点相对于其所属分布均值的偏离程度。其计算公式为：

$$Z = \frac{X - \mu}{\sigma} \qquad \text{(2-1)}$$

其中，$X$ 为某项指标在某个样本中的原始观测值，$\mu$ 为该指标在所有历史样本中的总体均值，$\sigma$ 为该指标的历史总体标准差。Z 值的数值含义是：原始值距离均值有多少个标准差。当 Z 值为正时，表示该原始值高于均值；当 Z 值为负时，表示低于均值；Z 的绝对值越大，偏离越显著。例如，某位患者谷氨酰转移酶的检验结果为 200 U/L，而该指标在所有历史样本中的均值为 30 U/L、标准差为 40 U/L，则该结果的 Z 值为 (200-30)/40 = 4.25，表示偏离均值 4.25 个标准差，属于相当偏离的水平。

Z-Score 标准化后的数据具有一个重要的数学性质：无论原始数据服从何种分布，标准化后的数据集均满足均值为 0、标准差为 1。这一性质使得不同量纲和量级的指标被映射到了同一坐标体系下，相互之间具备了可比性。在多指标联合分析中，Z-Score 标准化通常作为数据预处理的第一步，将各维度的原始值转换为无量纲的标准分数后再输入后续的模型。

本系统使用 Z-Score 算法对各项检验指标进行标准化处理，各指标的总体均值和标准差通过对历史检验数据的周期性统计获得，为后续的孤立森林多指标联合异常检测提供统一的量化输入。

### 2.3.2 孤立森林异常检测算法

在异常检测领域，传统统计方法（如 3σ 原则、箱线图 IQR 法）仅适用于单维度离群值判断，无法分析多变量之间的协同偏离；而有监督学习方法需要大量已标注的异常样本，在医疗检验场景中标注成本高昂且异常样本天然稀缺，实用性受限。

孤立森林（Isolation Forest）是由 Liu 等人于 2008 年提出的一种无监督异常检测算法。与大多数方法先"定义正常模型、再识别偏离样本"的策略相反，孤立森林直接利用"异常数据更容易被孤立"这一核心直觉——异常点在特征空间中通常疏离于密集区域，随机划分时少量分割即可将其隔离；而正常点聚集在密度高的区域，需要更多次分割才能被单独圈出。

算法由多棵孤立树（iTree）构成集成模型。每棵 iTree 的构建过程完全随机：从训练集中随机抽样一个子样本作为根节点，随机选取一个特征维度并在该维度的取值范围内随机确定一个分割值，按该分割值将样本二分为左子树和右子树，递归重复直到每叶节点仅包含单个样本或达到预设深度上限。由于构建过程不依赖任何距离或密度计算，算法具有线性的时间复杂度。检测时，待测样本沿每棵 iTree 从根节点遍历至叶节点，经历的边数即为该树的路径长度。对所有树的路径长度取均值后，通过归一化公式转换为 (0, 1) 区间内的异常分数——正常样本路径较长，分数趋近 0；异常样本路径较短，分数趋近 1。

异常分数 $s(x)$ 的计算公式为：

$$s(x, n) = 2^{-\frac{E[h(x)]}{c(n)}} \qquad \text{(2-2)}$$

其中 $E[h(x)]$ 为样本在所有树中的平均路径长度，$c(n)$ 为给定样本量下二叉搜索树平均路径的理论期望值，用于归一化处理。

本系统利用孤立森林算法对多项检验指标进行联合异常评分：先通过 Z-Score 消除各指标的量纲差异，再将标准化后的特征向量输入模型，根据异常分数输出正常、可疑或异常三级判定结果。

## 2.4 医疗数据合规规范

医疗信息系统的开发和运行不仅需要满足功能性和技术性指标，还必须严格遵守国家医疗行业相关的法律法规与行业规范。本系统在设计阶段即对照以下四部核心法规进行合规性审查。

（1）《医疗机构病历管理规定》（原卫生部 2013 年发布）明确了病历资料的保存、查阅、修改与封存规则。其中规定，门（急）诊病历保存期限自患者最后一次就诊之日起不少于 15 年，住院病历保存期限自患者最后一次出院之日起不少于 30 年。这意味着系统的逻辑删除机制必须确保数据在保存期限内的完整性，不能以物理删除方式处理历史记录。此外，该规定要求病历修改必须保留修改痕迹，明确记录修改人、修改时间及修改前后的内容。

（2）《中华人民共和国个人信息保护法》（2021 年实施）将医疗健康信息、生物识别信息列为敏感个人信息，明确要求处理敏感个人信息应当取得个人的单独同意，并采取加密、去标识化等安全保护措施。患者的身份证号、联系电话、家庭住址等个人信息，以及病情诊断等医疗健康信息，在信息系统中必须从采集、传输、存储、展示到销毁的全生命周期中受到保护。

（3）《医疗卫生机构网络安全管理办法》（国家卫生健康委 2022 年发布）对医疗卫生机构的信息安全管理、网络安全防护、数据安全保护和应急处置机制提出了系统性要求。办法要求机构按照网络安全等级保护制度进行系统定级和备案，对核心业务系统实施网络隔离、访问控制和入侵防范，建立数据备份与恢复机制，保留完整的网络安全日志。

（4）《医学检验实验室管理暂行办法》（原国家卫生计生委 2016 年发布）针对医学检验机构明确要求检验记录的原始性、完整性和可追溯性。检验结果录入后应当有据可查，任何修改必须保留修改前后的完整记录，确保检验结果的真实可靠。

本系统在设计中对上述合规要求进行了逐一落实：数据的删除操作统一采用逻辑删除机制，仅标记作废状态而不物理清除数据行；对患者身份证号和手机号采用 AES 加密存储，前端展示时自动脱敏；操作日志表仅开放查询接口，不提供修改和删除功能；实现了全量和增量相结合的自动数据库备份方案。
