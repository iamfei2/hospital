# 1.1 项目背景及意义

## 1.1.1 项目背景

随着医院信息化建设逐渐深入，智能化医疗分析慢慢成为行业主流[1]。在科室检查数据管理的过程中，积累的检查数据呈现出多类型、多格式的特征。这些数据涵盖放射科的 CT 影像报告与核磁共振报告、病理科的切片诊断记录、消化内镜科的肠镜检查记录，以及检验科的血常规、生化等实验室检验数据。传统基于 Excel 电子表格的手工数据管理模式在处理此类数据时，常出现查询效率低、数据准确性差、缺乏异常检测能力的问题。

第一，全院级信息系统在科室层面"水土不服"。国内大型医院普遍部署了 HIS、LIS、PACS 等全院级信息管理系统[2]，但这些系统功能冗余、部署成本高、操作流程复杂，主要面向全院统筹管理场景。科室医护人员的核心诉求——快速录入、便捷查询、简单统计——在全院级系统中往往需要经过繁琐的操作路径才能完成。科室级、轻量化的数据管理需求长期得不到满足。

第二，历史数据格式混乱，批量迁移困难。科室积累了数年甚至十余年的历史检查数据，分散在数十个 Excel 文件中。不同时期、不同人员的录入习惯导致字段命名不统一、日期格式混乱、数据类型不一致，个别文件还夹杂着合并单元格和手写备注。现有系统对无统一模板的非标准化 Excel 数据兼容性差，缺乏格式校验、重复检测、异常标记等批量导入质量保障机制，数据迁移的准确率和效率难以保证。

第三，数据查询与统计分析能力薄弱。在 Excel 管理模式下，医生查找某位患者的历史检查记录需要逐个文件翻阅，多条件组合筛选无法实现，耗时且容易遗漏。科室管理者进行月度工作量统计需要人工汇总数十个分散文件中的数据，效率低下且容易出错。诊断时无法快速获得患者检验指标的历史变化趋势，数据的潜在价值无法充分挖掘。

第四，数据安全与合规风险突出。Excel 文件缺乏细粒度的权限控制，操作记录无从追溯——谁在何时修改了什么数据完全不可知。文件可能被误删、覆盖或任意复制传播，患者姓名、身份证号、手机号码等敏感信息以明文形式存储。对照《医疗机构病历管理规定》和《个人信息保护法》关于病历保存期限不低于三十年、操作全程留痕可追溯的要求[3]，传统 Excel 管理模式在法律合规层面存在显著隐患。

第五，智能化分析能力缺失。传统管理完全依赖人工审核数据，检验指标异常靠检验技师和医生的个人经验判断，容易被遗漏。对于多项指标组合显示的潜在异常模式——例如血糖边缘偏高同时血红蛋白偏低——人工几乎无法识别。当异常结果出现时，没有自动通知机制，相关人员需要等到主动查看时才能发现，错过了及时干预的窗口期[4]。

为了解决上述问题，本文设计了一套基于前后端分离架构的医院检查数据管理平台，用于提升科室处理多类型检查数据的能力，为进一步的智能诊断提供支持。

## 1.1.2 国内外研究现状

### 国内研究现状

国内医疗信息化建设在新医改的推动下已进入高速发展阶段。大型医院普遍部署了医院信息系统（HIS）、实验室信息管理系统（LIS）、医学影像存档与通信系统（PACS）等核心医疗管理系统[5]，电子病历的覆盖率和应用水平逐年提升。在学术研究领域，现有成果多聚焦于全院级信息系统的集成架构与跨系统数据交换技术：王宁等[6]基于城轨列车监测数据设计了安全预测系统，探讨了异构监测数据的统一接入与分析方法；周亮瑾等[7]提出使用区块链与分布式数据库技术保障铁路旅客隐私，其去中心化存储、不可篡改日志等设计思路对医疗数据安全具有借鉴意义；孙泽奇等[8]基于大数据技术对道岔监测数据进行分析研究，在传感器数据的聚合统计与可视化方面积累了实践经验。

在医疗数据标准化方面，国内已逐步推行电子病历基本规范和数据元标准，大型三甲医院间通过区域健康信息平台实现了部分数据的跨机构共享[9]。然而，现有标准化工作主要关注全院级统一数据格式的制定与系统间接口规范的定义，针对科室层面长期积累的非标准化 Excel 历史台账数据的批量清洗、格式转换、去重校验与自动化迁移，专门的研究文献相对稀少[10]。在实际落地场景中，不同科室、不同时期的 Excel 台账在字段命名、日期格式、数据类型等方面的差异缺乏统一的处理范式，多数既有系统对此类数据的兼容性和容错能力均较弱。

在智能化医疗分析尤其是异常检测领域，国内学者已开展一系列研究。况鑫楠等[11]基于音频指纹设计了大数据的检索系统，在特征提取与相似度匹配方面取得了良好效果；高昕晟等[12]基于数字指纹设计了音频检索系统，其指纹比对方法对多时序数据的模式匹配具有参考价值。在临床检验数据异常检测方面，已有部分研究将统计过程控制（SPC）方法和孤立森林算法引入医疗数据质量监控，但多数成果仍停留在单项指标阈值告警层面[13]。对于多项检验指标之间存在潜在联合异常模式——如血糖边缘升高伴随血红蛋白偏低提示代谢紊乱——基于多维特征空间分析的深度检测研究尚不多见。此外，多数运营中的信息管理系统并未将实时预警推送功能作为标配来设计，从"数据入库"到"发现异常并主动通知"这一完整闭环的工程化实现仍存在缺口。

还有一个值得注意的维是，当前市面上面向中小医院的轻量级医疗信息系统在设计上偏向易部署与低门槛，但在操作全流程留痕、数据库自动备份恢复、细粒度分级权限管控等安全合规功能方面投入不足[14]。医疗数据管理系统若忽视合规底线，即便界面再简洁、操作再便捷，也难以在实际医疗场景中长期使用。

### 国外研究现状

国外医疗信息化起步较早，经过数十年持续投入，在医疗数据标准化建设、患者隐私保护和智能化管理应用等领域已形成较为成熟的学术成果与商业化生态[15]。

在数据标准化方面，国际上先后建立了医学数字成像与通信标准 DICOM 3.0 和医疗信息交换标准 HL7 FHIR，实现了不同厂商影像设备与异构信息系统之间的数据互联互通[16]。Kim S 等[17]比较了集中式与分布式处理系统在生物质精炼中的应用效果，讨论了不同架构在处理大规模异构数据时的效率差异；Chen H 等[18]对 FastDFS 客户端的小文件合并策略进行了优化研究，为解决大量分散小文件的存储与检索效率问题提供了技术方案。这些研究成果虽然面向不同领域，但其中对于异构数据的统一接入、格式标准化、大规模并发存取的解决思路，对多类型检查数据的管理系统设计具有方法论层面的参考价值。

在隐私保护方面，欧盟《通用数据保护条例》（GDPR）和美国《健康保险流通与责任法案》（HIPAA）从法律层面明确了医疗敏感数据的采集边界、存储要求和传输限制[19]。受此推动，国外商业化医疗软件普遍将数据加密、细粒度访问控制、全链路操作审计等技术作为标配集成，构建了多层次的患者隐私保护体系。Bielak K 等[20]在比较 Angular、React 和 Vue.js 三种前端框架的性能表现时指出，现代 Web 应用的安全防护已从服务器端延伸至客户端，前端对敏感数据的展示脱敏和传输加密同样构成隐私保护体系的重要一环。

在智能化管理方面，国外医疗数据管理系统已广泛融合人工智能与大数据分析技术。Meredova A[21]比较了 React 和 Vue 的服务端渲染能力，讨论了不同渲染策略对数据密集型页面的性能影响；Sheu A 等[22]对二型糖尿病患者的身体成分与胰岛素抵抗进行了流行病学关联分析，其利用多变量联合统计分析从电子健康档案中挖掘疾病风险因素的方法，展示了将历史医疗数据转化为临床见解的潜力。欧美头部厂商如 Epic、Cerner 等已将疾病风险预测、临床辅助决策等功能模块规模化落地于日常诊疗流程中，形成了从数据采集、清洗、分析到辅助决策的完整产品链[23]。

然而，国外成熟方案移植到国内科室实际场景中，至少存在三个层面的不匹配。一是成本层面——国外商业化医疗软件的单套采购费用与定制化服务成本对多数国内基层科室难以承受[24]。二是使用习惯层面——软件交互逻辑与表单设计依照欧美医疗机构的业务流程定制，与国内科室的工作习惯、审批制度存在差异，强行移植反而增加使用负担。三是标准层面——虽然国外已建立起成熟的医疗数据交换标准，但国内不同医院、不同院区甚至同一家医院的不同科室之间，信息系统品牌和版本迥异，真正实现统一标准仍是一个持续打磨中的长期目标[25]。

## 1.1.3 论文主要工作

根据研究背景所提到的医院检查科室缺乏统一数据管理平台与智能分析能力的问题，本论文主要围绕"构建一个面向医院科室、支持多类型检查数据全流程管理的数据平台与智能预警系统"这一目标展开。论文基于前后端分离架构，后端以 Spring Boot 为核心框架，配合 MyBatis-Plus 完成对象关系映射与数据持久化，引入 Redis 作为热点数据缓存层，前端采用 Vue.js 和 Element UI 搭建交互界面，最终交付了一套轻量化、可在医院内网环境独立部署的科室级数据管理平台。围绕上述目标，论文的主要研究工作分为以下五个方面展开。

第一，日常诊疗数据的全流程闭环管理。针对科室日常运转中最基础的增删改查需求，系统覆盖了患者电子档案的创建与动态维护、CT 检查、核磁检查、病理检查与肠镜检查四类医技记录的独立管理、检验结果逐项登记与多项目批量提交，以及临床医嘱的开具与修订。每条检查记录均支持 PDF 报告附件的上传与在线调阅，附件元信息随业务记录一同归档。所有数据的修改与作废操作均采取逻辑删除策略，配合 AOP 切面自动比对并记录修改前后的数据差异，形成可追溯的变更链条，从源头上补齐了 Excel 管理模式下的操作留痕缺口。

第二，历史数据的自动化迁移与多维度检索。针对科室长期积累的非标准化 Excel 台账，论文设计了一套基于 EasyExcel 流式读取与自定义 XML 解析器的批量导入机制。导入过程中依次执行格式合规校验、数值范围校验和数据库重复检测三道质量关卡，并区分严格模式与跳过模式以适应不同数据质量场景。导入结束后系统自动生成包含行级失败原因的导入报告，支持以 CSV 格式下载以供修正。在数据入库之后，患者与检查记录的查询不再受限于单个文件的翻找——系统提供了支持患者编号、姓名、检查部位、医生、科室、检查时间范围等多个维度自由组合的筛选面板，不同条件以逻辑与关系叠加，查询结果秒级返回。针对日常工作中反复使用同一组筛选条件的情况，系统还提供了查询模板的保存、共享与一键复用功能。

第三，检验数据的多指标联合异常检测。区别于简单的高低阈值比对，论文设计了一种"阈值告警 + 无监督异常检测"的双轨互补策略。在阈值层面，引入 Easy Rules 轻量级规则引擎，科室管理人员可通过前端页面动态配置各项检验指标的预警阈值与告警等级，规则的热更新不依赖代码重新部署，定时扫描任务自动拉取最新配置并匹配新入库数据。在联合检测层面，基于孤立森林算法从零实现了一套面向多检验指标的异常评分模型：先从历史正常样本中提取各指标的均值和标准差并完成 Z-Score 标准化，消除跨指标的量纲障碍；再以多维标准化向量为输入构建由一百棵孤立树组成的森林模型，通过计算样本在所有树中的平均路径长度得出其异常分数；最终融合 Z-Score 偏离值与孤立森林得分，输出"正常 / 可疑 / 异常"三级判断结论并列出贡献度最高的偏离指标，为临床医生提供可解释的辅助参考信息。

第四，科室管理数据的统计分析与可视化。为替代人工按月汇总数个 Excel 文件的高成本操作，系统将统计聚合下沉到数据库层，利用 SQL 的 GROUP BY 和聚合函数按时间周期、执行科室、检查类别和执行医生四个维度分别计算工作量数据，在十万条记录规模下单次统计耗时控制在两秒以内。统计结果通过 ECharts 渲染为柱状图、饼图和折线图等形式在前端展示，图表支持鼠标悬浮查看数值详情、图例筛选和区域缩放等交互操作。各维度的统计报表和当前查询结果均支持一键导出为 Excel 文件，EasyExcel 的分批写入机制保证了大数据量导出不会引发内存溢出。

第五，系统安全防护与运维支撑。在访问控制上，论文实现了 JWT 无状态身份认证与 RBAC 角色权限模型的双层防护，预设系统管理员、医生、检验技师和审计员共四类角色并设计了十六项覆盖各业务模块的细粒度操作权限编码，越权请求在拦截器层即被拦截并返回禁止访问状态。在全流程审计上，采用 Spring AOP 注解式编程模式，对标注了自定义注解的每一个业务方法进行环绕拦截，异步记录操作人、IP 地址、操作时间、操作类型及修改前后的完整数据快照，日志数据仅开放查询出口、不提供修改与删除途径，满足医疗行业对数据操作全程留痕的合规要求。在数据容灾上，设计了每日凌晨全量备份与午间增量备份相结合的双轨自动备份策略，备份文件经过 AES 加密和 GZIP 压缩后归档，自动清理超出保留期限的历史备份以控制磁盘占用，管理员可通过前端页面选择备份文件并输入动态验证码完成一键恢复。此外，系统预留了标准 RESTful 对外接口，第三方系统持有效 API Key 和签名即可按患者编号拉取其完整检查数据汇总，接口层集成了基于 Redis 滑动窗口的调用频率限制和异常熔断机制，在保障数据开放共享的同时防范滥用。

## 1.1.4 论文的组织安排

本论文共分七章，各章节内容安排如下：

第一章为绪论，主要介绍了医院检查数据管理平台的项目开发背景及当前科室数据管理面临的问题，综述了国内外医疗信息化领域的研究现状，并对论文的主要研究内容和组织结构进行了说明。

第二章为技术理论基础，系统性地介绍了系统开发过程中所使用的关键技术，包括 Spring Boot 后端框架、MyBatis-Plus 数据持久化技术、Z-Score 标准化与孤立森林异常检测算法、Easy Rules 规则引擎，以及 Vue.js、Element UI 等前端技术。

第三章为系统需求分析，将平台拆分为日常诊疗、智能查询与辅助诊断、预警监控、统计分析报表、系统运维管理五大业务模块，逐一梳理了各模块的功能性需求，同时从性能指标、安全防护、可维护性与易用性等方面明确了系统的非功能性约束。

第四章为系统概要设计，确立了"访问层—接入层—应用层—基础能力层—数据存储层"的五层技术架构，对上述五个模块进行了职责划分与功能边界定义，并完成了包括十七张核心业务表、RBAC 权限五表在内的完整数据库结构设计与高频查询索引规划。

第五章为系统详细设计与实现，分别阐述了横切全系统的安全认证基础设施（JWT 认证、RBAC 鉴权与 AOP 操作留痕），以及围绕上述五大模块的七节具体实现——将批量数据导入导出独立成节以突出工程化亮点，并针对基于 EasyExcel 的流式导入与三道校验机制、基于孤立森林与 Z-Score 的多指标联合异常检测、基于 Easy Rules 与 WebSocket 的双引擎实时预警等技术难点展开了详细论述。

第六章为系统测试与验证，从功能完整性、异常检测准确率、数据校验可靠性和系统安全性四个维度设计了测试用例，借助 JUnit、JMeter 和 OWASP ZAP 完成了功能测试、性能压测与安全扫描，结合医院科室的小规模试点部署验证了平台在真实业务场景下的可用性。

第七章为总结与展望，对系统在科室级多类型检查数据全生命周期管理、非标准化 Excel 与 XML 历史数据批量迁移、多指标联合异常检测与实时预警等方面取得的成果进行了归纳，同时反思了孤立森林模型在样本量较少时的训练稳定性等局限，并对后续引入深度学习模型、扩展多院区协同等方向进行了展望。
