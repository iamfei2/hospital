## 5.1 检查检验日常数据管理模块

该模块是整个系统的数据基底，后续所有的查询、统计、预警操作都建立在这里产生的数据之上。实现上采用 Spring MVC 经典的三层结构——Controller 负责接收参数和封装响应，Service 承载全部业务规则，Mapper 借助 MyBatis-Plus 完成持久化。四个子功能共用这条技术路线，下面按患者管理、检查管理、检验管理和医嘱管理的顺序分别展开。

### 5.1.1 患者信息管理

患者管理的入口是 PatientController，它对外暴露新增、修改、作废、恢复和全景视图五个 REST 接口。新增时，前端将表单字段打包为 JSON 提交到 /patient/save，Controller 校验身份证号格式后转交 PatientServiceImpl 处理。Service 层在入库前通过雪花算法生成一个以 P 开头、全局唯一的 patientId，再将 isInvalid 置为 false 代表有效记录，最后通过 PatientMapper.insert 写入数据库。

这里比较关键的设计是患者的全景视图接口。传统模式下医生要了解一位患者的全部就诊历史，需要在分散的 Excel 文件里逐个翻找，效率很低。为了在系统中解决这个问题，PatientController 提供了一个 aggregatePatientOverview 方法，内部并发调用 CtExaminationMapper、MriExaminationMapper、EnteroscopyExaminationMapper、PathologyExaminationMapper、LabResultMapper 和 MedicalOrderMapper 六个 Mapper 的查询方法，把该患者关联的所有检查记录、检验结果和医嘱记录一次性取出来，按时间降序排列后统一返回前端，前端用一个带时间轴样式的卡片面板渲染。

### 5.1.2 检查记录管理

四种检查类型（CT、核磁、肠镜、病理）在代码层面分别独立但结构完全对称，每种类型配一组 Controller-Service-Mapper-Entity 四件套。以 CT 检查为例，CtExaminationController 负责暴露 /ctExamination/save、/ctExamination/update、/ctExamination/delete 等标准 CRUD 接口，内部路径走到 CtExaminationServiceImpl 去处理业务规则，最终通过 CtExaminationMapper 与数据库表中的 ct_examination 完成交互。

检查管理有两个值得单独讨论的设计点：作废机制和附件上传。作废不是真的从数据库里删掉一行，而是把 isInvalid 字段从 false 翻成 true。前端所有查询请求——不管是列表查询还是详情查询——后端一律在 QueryWrapper 里自动拼上 isInvalid = false 作为默认过滤条件，因此作废后的记录对用户来说就从界面上消失了。但数据物理层面还在，管理员在操作日志里能查到这条记录完整的作废前后状态，必要时还可以通过 restore 接口把它重新标记为有效。图 5-5 以活动图的方式展示了作废操作的前后校验和状态切换流程。

```

:点击"作废"按钮;
:前端弹出二次确认对话框;

  stop
endif

:Service层查询当前记录的isInvalid状态;

附件上传的思路比较简单。前端用了 Element UI 的 el-upload 组件，选择 PDF 文件后直接 POST 到对应 Controller 的 upload 方法。后端先把文件重命名为"当前时间毫秒值_原始文件名"以避免覆盖，再按照检查类型存到 uploads 目录下的子文件夹（比如 uploads/ct/、uploads/mri/），最后把文件的访问路径写回该条检查记录的 storageUrl 字段。前端预览时，浏览器向 download 接口发 GET 请求，后端以字节流方式读出文件内容并将 Content-Type 响应头设为 application/pdf，浏览器收到后直接在当前页或新标签页中以 PDF 查看器的方式内联打开，不需要跳出系统。

从图 5-7 中能看到 LabResultServiceImpl 聚合了四个依赖项——除了正常的 LabResultMapper 和 LabItemDictMapper 之外，它还直接持有了预警引擎和统计计算两个服务的引用。这个设计的意图是在一次检验结果保存成功之后，紧跟着自动完成两件事：一是把新数据喂给统计引擎，让它增量更新该项目的历史均值和标准差，保证 Z-Score 基准的实时性；二是把新数据传给预警引擎，由它遍历当前启用的所有规则进行实时评估，有命中的立刻生成预警记录并推送。

批量登记是单条录入的增强版。前端允许用户在同一张表单上勾选多个检验项目，一次性填写所有结果值后统一提交。后端收到的是一个 LabResult 数组，Service 层用 @Transactional 注解包裹整个操作——要么数组里的每一条都成功写入，要么一条都不写，全部回滚。之所以加事务控制，是因为批量提交本身就是一个原子操作单元：如果因为其中某条记录的数据格式错误导致部分写入部分失败，会产生"患者今天查了血糖和血红蛋白，系统里却只存了血糖没存血红蛋白"的数据缺失问题，这在医疗场景中是绝对不允许的。

图 5-8 用序列图描述了从批量提交到异步触发预警的完整交互路径。

```

从图 5-8 中能看到一个很重要的设计取舍：updateStatisticsOnNewResult 是同步执行的，而 evaluate（预警评估）是异步的。这样设计的理由是统计基准的更新量极小——每次只重算当前检验项目对应科室的均值和标准差，几十毫秒之内就能完成，走同步路线对接口响应时间的影响几乎可以忽略不计；而预警评估需要遍历全部已启用的规则，规则数量不确定，匹配逻辑中可能还包含对历史数据的二次查询，走异步路线能保证主业务返回速度不受规则数量变化的影响。

## 5.2 多维度查询与智能分析模块

该模块解决的是"数据存进去了怎么快速找到"以及"数据里藏着什么信息"这两个问题。三个子功能——多条件组合查询、指标趋势图表、多指标联合异常检测——分别从不同层面提升了数据的可用价值。

### 5.2.1 多条件组合查询

查询功能的核心不在算法，而在 SQL 的构建策略。前端查询面板上摆了患者编号、患者姓名、检查部位、执行科室、检查医生、起止时间六个独立的条件输入控件，用户填哪个算哪个，没填的不参与查询。图 5-11 以活动图展示了从用户填写条件到返回分页结果的完整链路。

```
@startuml 图5-11 多条件组合查询活动图
start
:用户进入查询面板;
:在任意个输入框中填入筛选条件;
:点击"查询"按钮;
:前端将非空条件组装为JSON;
:POST /ctExamination/page;
:Controller接收QueryParam;
:调用Service层queryPage();
:创建QueryWrapper空壳;

  :wrapper.eq("patient_id", patientId);
endif

  :wrapper.like("patient_name", patientName);
endif
if (timeRange非空?) then (是)
  :wrapper.between("examination_time", start, end);
endif
if (examineDept非空?) then (是)

图 5-11 很直观地说明了这种"空条件就不拼"的策略。其对应的代码在 CtExaminationServiceImpl 里大致是这样的——每个 if 块独立判断，绝不在 QueryWrapper 上添加不需要的条件。这种写法的优势是生成的 SQL 非常干净：如果用户只选了科室和起止时间，最终的 WHERE 子句只包含三行条件（科室=某值、时间在某某区间、且未作废），MySQL 优化器可以精确地选择 examine_dept 上的索引作为驱动条件，再用 examination_time 上的索引做范围扫描，最终的 rows examined 量非常小。实际测试中，在 ct_examination 表堆积了约五万条数据后，一次两条件的组合查询执行耗时在 200 到 300 毫秒之间。

### 5.2.2 检验指标趋势分析

趋势分析的功能定位很明确——给临床医生提供一种直观查看患者某项指标长期动态变化的手段，尤其适用于糖尿病、高血压这类需要持续监测的慢病管理场景。

前端的交互入口放在患者详情页中。医生选定患者和检验项目后，前端向 /labResult/getTrend 接口发送请求，携带 patientId 和 itemId 两个参数。后端 LabResultController 转到 LabResultServiceImpl.getTrendData 方法，该方法通过 LabResultMapper 的 selectByPatientAndItem 方法查到该患者在该项目上的全部历史检验记录，按 reportTime 升序排列，每条记录提取 reportTime、resultValue、resultUnit 和 normalRange 四个字段封装为 TrendVO 对象，以列表形式返回。

### 5.2.3 多指标联合异常检测

图 5-16 用活动图完整描述了联合检测的三个阶段——Z-Score 标准化、孤立森林评分和加权融合判定，这是整个系统中最核心的算法流程。

```
@startuml 图5-16 多指标联合异常检测活动图
start
:调用jointDetect(patientId, ruleId);
:从规则配置中读取itemIds\n(如"16981,16982,16985");
:查询该患者最近一次含这些项目的检验结果;
if (检验数据缺失?) then (是)
  :返回"数据不足，无法检测";
  stop
endif
partition "第一阶段：Z-Score单指标标准化" {
  :遍历每一个检验项目;
  :从labItemStatistics表\n获取μ(均值)和σ(标准差);
  :对每个项目计算 Z=(x-μ)/σ;
  :筛选|Z|>2.0的项目作为异常候选;
}
partition "第二阶段：孤立森林多维评分" {
  :将各项目的Z-Score值\n组合为一维特征向量;
  :加载该规则对应的\n已训练IsolationForest模型;
  :遍历100棵孤立树计算路径长度;
  :计算平均路径长度E(h);
  :得分=2^{-E(h)/c(n)};
}
partition "第三阶段：加权融合与等级判定" {
  :计算Z-Score异常指标的平均|Z|;
  :归一化至[0,1]区间：min(avg|Z|/4, 1.0);
  :combinedScore = 0.4×Znorm + 0.6×IFscore;
  if (combinedScore>=0.6) then (是)
    :等级=ANOMALY(异常);
  elseif (combinedScore>=0.4) then (是)
    :等级=SUSPICIOUS(可疑);
  else (默认)
    :等级=NORMAL(正常);
  endif
}
:返回异常等级和异常指标清单;
stop
@enduml
```



从图 5-16 中可以清楚地看出，第一阶段做的是把不同检验项目的数值拉到同一个尺度上比较。举个例子：血糖的参考范围在 3.9 到 6.1 之间，血小板计数在 100 到 300 之间，两者的单位和正常区间完全不同，如果直接用原始值拼接特征向量，血小板 200 和血糖 6.0 这两个数在数值尺度上差距太大，算法会被大量纲数值主导。经过 Z-Score 标准化后，血糖 6.0（假设均值 5.0，标准差 0.5）变成 Z=2.0，血小板 200（假设均值 200，标准差 30）变成 Z=0，两者处于同一数量级，后面孤立森林才能公平地处理。

第二阶段孤立森林的具体实现在 IsolationForest 类里面。这个类是完全用原生 Java 写的，没有依赖任何第三方机器学习库。其 buildForest 方法从训练数据中随机采样 256 条，对每条样本随机抽取一个特征索引和一个在该特征值域内的随机分裂值，递归往下构建二叉树，深度达到 10 或者节点内样本数不足 2 时停止分裂。这样造出 100 棵"随意长"的树，然后预测时让待检测样本走每棵树，统计从根节点掉到叶子节点经历的步数（即路径长度），步数越短说明这个点越容易被随机切分出来，越有可能是异常点。

## 5.3 智能预警与实时推送模块

### 5.3.1 预警规则引擎

预警引擎运转的核心逻辑集中在 WarningEngineServiceImpl.evaluate 方法里。检验结果入库后，LabResultServiceImpl 以异步方式调用它，传入新保存的 LabResult 对象。evaluate 方法做的第一件事是从数据库拉取当前所有 enabled 状态为 true 的预警规则，然后按 ruleType 字段筛出类型为 LAB 且 itemId 与当前检验项目匹配的那部分，再逐条扔给 evaluateRule 去做条件匹配。

evaluateRule 方法内部做了一次策略派发——根据 conditionType 的不同取值走向不同的判断分支。图 5-20 用序列图完整展示了从规则筛选到条件派发再到去重和推送的全过程。

```
@startuml 图5-20 预警规则评估序列图

```



图 5-20 中的一个重要细节是去重条件的设计。30 分钟的窗口长度来自经验设定——同一个患者在半小时内不太可能有两次独立的检验，如果同一规则反复触发，基本可以判断为同一条检验结果被逻辑重跑导致的重复报警，而非新的临床事件。四个去重条件（患者 ID、项目 ID、规则 ID、30 分钟窗口）缺一不可，且额外加上"未读"状态——意味着如果医生已经点开这条预警查看了，说明已经知晓该异常，之后相同的异常可以在下次触发时再次提醒，不需要永久抑制。

### 5.3.2 关键词预警与定时扫描

关键词预警的处理逻辑相对简单。当检查报告保存后，业务层调用 WarningEngineServiceImpl.evaluateExamination 方法，传入患者信息、检查类型和报告结论文本。方法取出所有 ruleType 为 KEYWORD 的启用规则，将每条规则预设的关键词与报告结论字符串做不区分大小写的包含匹配，命中了就产出预警记录并推送。这个功能的设计灵感来自一个真实痛点——低年资医生在书写报告时，可能在结论中写入了"占位性病变"或"考虑肿瘤"这类带有严重病变倾向的措辞，但因为经验不足或者忙于接诊，没有主动向上级汇报，而系统可以自动捕获这些关键词并提醒科室管理层关注。

定时扫描的任务则集中在 WarningScannerTask 类中，由两个 @Scheduled 方法驱动。scanMissingData 每 30 分钟触发一次，逻辑是用 Patient 表遍历所有 isInvalid 为 false 的患者，对每位患者查一次其最近检验结果的 reportTime，如果距今已经超过规则中配置的 missingDays 天数阈值，就生成一条 MISSING 类型的预警；scanOperationAnomaly 每 15 分钟触发一次，逻辑是提取过去 5 分钟内全部操作日志记录，筛选出类型为"删除"或"作废"的记录，数其条数，如果超出规则中 thresholdHigh 设定的上限（默认 10 条），就判定为批量异常操作并预警，同时额外检查当前时间是否在非工作时段的范围内（22:00 至次日 06:00 以及周六周日），如果是且存在任何操作记录，也一并触发预警。

图 5-23 用序列图完整说明了 WebSocket 从建立连接到接收预警消息的生命周期。

从图 5-23 可以看到，服务端使用了 JSR 356 标准的 @ServerEndpoint("/ws/warning/{userId}") 注解来声明 WebSocket 端点。前端在用户登录成功后立刻创建 WebSocket 连接，URL 中的 userId 取自 localStorage 中保存的登录用户 ID。服务端持有的是一个 ConcurrentHashMap<String, Session>，键是 userId，值是对应的 WebSocket Session。预警推送时，broadcast 方法遍历 Map 中所有 Entry，对每个 Session 调用 getBasicRemote().sendText 方法将 JSON 字符串发送到客户端。客户端的 onmessage 回调接收消息后，调用 Element UI 的 this.$notify 方法在屏幕右上角弹出预警通知框，同时更新顶部导航栏的预警徽标数字。

## 5.4 可视化统计与报表导出模块

### 5.4.1 统计图表

统计功能的实现分成两段：后端负责按维度做 GROUP BY 聚合，前端负责拿聚合数据渲染图表。后端核心在 StatisticsController 中，以 /statistics/countByTypes 接口为例，该接口接收四个参数：科室编码（deptCode）、开始日期（startDate）、结束日期（endDate）和时间粒度（period，取值为 day/week/month）。ServiceImpl 实现中根据 period 的值选择不同的 DATE_FORMAT 格式化字符串——日粒度用 '%Y-%m-%d'，周粒度用 '%Y-%u'，月粒度用 '%Y-%m'——然后对四张检查主表（ct_examination、mri_examination、enteroscopy_examination、pathology_examination）分别执行带 GROUP BY 的 COUNT 聚合，汇总成一个包含四种检查类型分项统计的 result 对象返回。

前端 StatisticsA.vue 组件在 mounted 生命周期里调用 echarts.init 绑定页面上预设的 div 容器，拿到后端数据后调 setOption 更新图表。柱状图的 xAxis.data 取的是部门名或医生名列表，series 里每种检查类型一条柱子，方便横向对比不同科室或医生的工作量。饼图则取所有检查类型的合计值，展示各自占总量的百分比。

图 5-25 中展示了四条独立的 GROUP BY 统计拼成一个综合结果的流程。之所以不对四张表做 UNION ALL 合并成一张中间表再 GROUP BY——这是考虑到四张表的索引策略各不相同，合并成大表后再聚合会导致索引失效。

## 5.5 数据导入与系统运维保障模块

### 5.5.1 Excel 批量导入

Excel 导入功能的设计核心在于"逐行处理、批量写库、大量数据不爆内存"。EasyExcel 官方提供的 AnalysisEventListener 继承模式天然支持这一目标——监听器的 invoke 方法被回调时，SAX 解析器只将当前这一行的数据注入内存，前一行已被处理过的数据已经被 GC 回收，因此在读取 1 行和读取 5 万行的真实内存占用几乎没有差别。导入过程中校验逻辑集中在 invoke 方法内部，每行被解析出来之后立即走一遍必填字段检查、日期格式验证、数值格式验证、项目代码字典对照和文件内去重五道关卡，任何一关不过就记录该行失败并跳过，而不会导致整个导入过程中断。

记录通过校验后先进入内存中的 List 缓冲区，缓冲区涨到 500 条时触发一次 MyBatis-Plus 的 saveBatch 批量写库，写完后 list.clear() 清空，让 GC 回收这 500 条对象的空间，然后 List 继续接收新数据。图 5-28 用活动图完整描绘了这个"读一行→验一行→暂存→满 500 写一批→清空继续"的循环。

```
@startuml 图5-28 Excel批量导入活动图

:用户选择Excel文件并设置导入模式;
:文件上传至ImportController;
:EasyExcel.read(file, listener).sheet().doRead();

### 5.5.3 操作审计 AOP 设计

操作审计是跨越所有模块的横向功能，其实现借用了 Spring AOP 的环绕通知能力。定义上，@OperateLog 注解有三个属性——operationType（操作类型，如"新增""修改""删除""作废"）、operatedTable（操作的数据表名，如"patient""lab_result"）和 description（操作描述）。凡是需要被审计的 Controller 方法，标上这个注解即可，无需在方法体内额外写任何日志相关的代码。

从图 5-33 可以清楚地看到，审计日志的写入和业务返回之间没有因果关系——即使用了 @Async，日志保存是独立线程执行的，业务返回不等待它。这样设计的直接效果是，即使操作日志表所在的数据库节点临时不可用，主业务流程仍然能正常运行并返回成功，不会因为审计功能的异常拖垮整个系统。

### 5.5.4 RBAC 权限管控

权限管控的数据模型围绕四张表展开：sys_permission 存十六项细粒度权限（编码如 patient:view、ct:manage、warning:manage），sys_role 存四个预置角色（系统管理员、医生、检验技师、审计员），sys_role_permission 建立角色与权限的多对多映射，sys_user_role 建立用户与角色的多对多映射。

权限校验的工作发生在 JwtInterceptor 中。Token 校验成功后，取出当前用户的 userId，判断其角色：如果角色是 admin，直接 return true 跳过所有检查；否则，将当前请求的 URI 与预设的路径-权限编码映射表（一个静态 Map<String, String>，存储着 /patient → patient:view、/ctExamination → ct:view 等十五对映射关系）做匹配，取出该路径对应的权限编码，再调用 PermissionServiceImpl.hasPermission 查询该用户是否拥有此权限。PermissionServiceImpl 内部维护了一个 ConcurrentHashMap 作为本地线程安全的权限缓存，键是 userId，值是 List 权限编码集合，首次查询时从数据库加载后写入缓存，之后直接从缓存返回，权限变更时手动调用 clearCache 清除指定用户的缓存让其下次查询时重新加载。

```
@startuml 图5-35 RBAC权限校验序列图
actor 用户
participant "JwtInterceptor" as JWT
participant "PermissionServiceImpl" as PS
participant "PermissionMapper" as PM
database MySQL

用户 -> JWT: HTTP请求到达
JWT -> JWT: 验证JWT Token
JWT -> JWT: 提取userId和role
alt role = "admin"
  JWT -> JWT: 直接放行
else 其他角色
  JWT -> JWT: URI映射为权限编码\n如 /ctExamination → ct:view
  JWT -> PS: hasPermission(userId, "ct:view")
  PS -> PS: 查缓存 permissionCache.get(userId)
  alt 缓存命中
    PS --> JWT: true/false
  else 缓存未命中
    PS -> PM: selectPermissionCodesByUserId(userId)
    PM -> MySQL: SELECT DISTINCT p.code\nFROM sys_permission p\nJOIN sys_role_permission rp...\nJOIN sys_user_role ur...\nWHERE ur.user_id=?

    PS --> JWT: true/false
  end

    JWT -> JWT: return true 放行
  else 权限不足
    JWT -> JWT: response.setStatus(403)
    JWT --> 用户: {"code":403,"msg":"权限不足"}
  end

@enduml
```



图 5-35 完整展示了权限校验的两种路径：admin 角色直接走快速通道，其他角色走 RBAC 验证通道。缓存的设计大幅降低了权限查询对数据库的访问频率——在科室 10 人并发的场景中，如果没有缓存，每次请求都需要执行一条三表 JOIN 的 SELECT 语句，平均耗时约 15 到 20 毫秒，而命中缓存后耗时降低到 0.1 毫秒以下，几乎不产生可感知的延迟。

### 5.5.5 数据库备份与恢复

备份功能由 BackupService 全权负责。全量备份时，backup 方法调用 Runtime.exec 启动系统后台进程执行 mysqldump 命令，通过 --single-transaction 选项保证 InnoDB 存储引擎下的事务一致性读，--routines 和 --triggers 确保存储过程和触发器同样被导出。导出的 SQL 文本通过 InputStream 读取到 byte[] 数组中，先经 GZIPOutputStream 压缩，再用 AES/GCM 模式加密（加密过程中使用每次生成的 12 字节随机 IV，密钥从 application.yml 配置中读取），最终写入 uploads/backups 目录下命名为"当前时间戳_enc_backup.bak.gz"的文件。增量备份的执行逻辑几乎相同，唯一的区别在于 mysqldump 命令中附加了 --where="create_time > '上次备份时间' OR update_time > '上次备份时间'" 参数，仅导出增量变化的数据行而非整张表。

加密算法选用 AES/GCM 而非更常见的 AES/CBC 的理由是，GCM 模式在加密的同时附带生成 128 位的认证标签，这个标签能用来验证密文在存储和传输过程中是否被篡改过，即便攻击者改了备份文件里 1 个字节，恢复时校验也会报错，避免因备份文件损坏或恶意篡改导致的数据库恢复异常。

```
@startuml 图5-37 备份恢复活动图

## 5.1 检查检验日常数据管理模块

该模块是整个系统的数据基底，后续所有的查询、统计、预警操作都建立在这里产生的数据之上。实现上采用 Spring MVC 经典的三层结构——Controller 负责接收参数和封装响应，Service 承载全部业务规则，Mapper 借助 MyBatis-Plus 完成持久化。四个子功能共用这条技术路线，下面按患者管理、检查管理、检验管理和医嘱管理的顺序分别展开。

### 5.1.1 患者信息管理

患者管理的入口是 PatientController，它对外暴露新增、修改、作废、恢复和全景视图五个 REST 接口。新增时，前端将表单字段打包为 JSON 提交到 /patient/save，Controller 校验身份证号格式后转交 PatientServiceImpl 处理。Service 层在入库前通过雪花算法生成一个以 P 开头、全局唯一的 patientId，再将 isInvalid 置为 false 代表有效记录，最后通过 PatientMapper.insert 写入数据库。

这里比较关键的设计是患者的全景视图接口。传统模式下医生要了解一位患者的全部就诊历史，需要在分散的 Excel 文件里逐个翻找，效率很低。为了在系统中解决这个问题，PatientController 提供了一个 aggregatePatientOverview 方法，内部并发调用 CtExaminationMapper、MriExaminationMapper、EnteroscopyExaminationMapper、PathologyExaminationMapper、LabResultMapper 和 MedicalOrderMapper 六个 Mapper 的查询方法，把该患者关联的所有检查记录、检验结果和医嘱记录一次性取出来，按时间降序排列后统一返回前端，前端用一个带时间轴样式的卡片面板渲染。

## 5.2 多维度查询与智能分析模块

该模块解决的是"数据存进去了怎么快速找到"以及"数据里藏着什么信息"这两个问题。三个子功能——多条件组合查询、指标趋势图表、多指标联合异常检测——分别从不同层面提升了数据的可用价值。

### 5.2.2 检验指标趋势分析

趋势分析的功能定位很明确——给临床医生提供一种直观查看患者某项指标长期动态变化的手段，尤其适用于糖尿病、高血压这类需要持续监测的慢病管理场景。

前端的交互入口放在患者详情页中。医生选定患者和检验项目后，前端向 /labResult/getTrend 接口发送请求，携带 patientId 和 itemId 两个参数。后端 LabResultController 转到 LabResultServiceImpl.getTrendData 方法，该方法通过 LabResultMapper 的 selectByPatientAndItem 方法查到该患者在该项目上的全部历史检验记录，按 reportTime 升序排列，每条记录提取 reportTime、resultValue、resultUnit 和 normalRange 四个字段封装为 TrendVO 对象，以列表形式返回。

### 5.2.3 多指标联合异常检测

图 5-16 用活动图完整描述了联合检测的三个阶段——Z-Score 标准化、孤立森林评分和加权融合判定，这是整个系统中最核心的算法流程。

```
@startuml 图5-16 多指标联合异常检测活动图
start
:调用jointDetect(patientId, ruleId);
:从规则配置中读取itemIds\n(如"16981,16982,16985");
:查询该患者最近一次含这些项目的检验结果;
if (检验数据缺失?) then (是)
  :返回"数据不足，无法检测";
  stop
endif
partition "第一阶段：Z-Score单指标标准化" {
  :遍历每一个检验项目;
  :从labItemStatistics表\n获取μ(均值)和σ(标准差);
  :对每个项目计算 Z=(x-μ)/σ;
  :筛选|Z|>2.0的项目作为异常候选;
}
partition "第二阶段：孤立森林多维评分" {
  :将各项目的Z-Score值\n组合为一维特征向量;
  :加载该规则对应的\n已训练IsolationForest模型;
  :遍历100棵孤立树计算路径长度;
  :计算平均路径长度E(h);
  :得分=2^{-E(h)/c(n)};
}
partition "第三阶段：加权融合与等级判定" {
  :计算Z-Score异常指标的平均|Z|;
  :归一化至[0,1]区间：min(avg|Z|/4, 1.0);
  :combinedScore = 0.4×Znorm + 0.6×IFscore;
  if (combinedScore>=0.6) then (是)
    :等级=ANOMALY(异常);
  elseif (combinedScore>=0.4) then (是)
    :等级=SUSPICIOUS(可疑);
  else (默认)
    :等级=NORMAL(正常);
  endif
}
:返回异常等级和异常指标清单;
stop
@enduml
```



从图 5-16 中可以清楚地看出，第一阶段做的是把不同检验项目的数值拉到同一个尺度上比较。举个例子：血糖的参考范围在 3.9 到 6.1 之间，血小板计数在 100 到 300 之间，两者的单位和正常区间完全不同，如果直接用原始值拼接特征向量，血小板 200 和血糖 6.0 这两个数在数值尺度上差距太大，算法会被大量纲数值主导。经过 Z-Score 标准化后，血糖 6.0（假设均值 5.0，标准差 0.5）变成 Z=2.0，血小板 200（假设均值 200，标准差 30）变成 Z=0，两者处于同一数量级，后面孤立森林才能公平地处理。

第二阶段孤立森林的具体实现在 IsolationForest 类里面。这个类是完全用原生 Java 写的，没有依赖任何第三方机器学习库。其 buildForest 方法从训练数据中随机采样 256 条，对每条样本随机抽取一个特征索引和一个在该特征值域内的随机分裂值，递归往下构建二叉树，深度达到 10 或者节点内样本数不足 2 时停止分裂。这样造出 100 棵"随意长"的树，然后预测时让待检测样本走每棵树，统计从根节点掉到叶子节点经历的步数（即路径长度），步数越短说明这个点越容易被随机切分出来，越有可能是异常点。

## 5.3 智能预警与实时推送模块

### 5.3.1 预警规则引擎

预警引擎运转的核心逻辑集中在 WarningEngineServiceImpl.evaluate 方法里。检验结果入库后，LabResultServiceImpl 以异步方式调用它，传入新保存的 LabResult 对象。evaluate 方法做的第一件事是从数据库拉取当前所有 enabled 状态为 true 的预警规则，然后按 ruleType 字段筛出类型为 LAB 且 itemId 与当前检验项目匹配的那部分，再逐条扔给 evaluateRule 去做条件匹配。

evaluateRule 方法内部做了一次策略派发——根据 conditionType 的不同取值走向不同的判断分支。图 5-20 用序列图完整展示了从规则筛选到条件派发再到去重和推送的全过程。

图 5-20 中的一个重要细节是去重条件的设计。30 分钟的窗口长度来自经验设定——同一个患者在半小时内不太可能有两次独立的检验，如果同一规则反复触发，基本可以判断为同一条检验结果被逻辑重跑导致的重复报警，而非新的临床事件。四个去重条件（患者 ID、项目 ID、规则 ID、30 分钟窗口）缺一不可，且额外加上"未读"状态——意味着如果医生已经点开这条预警查看了，说明已经知晓该异常，之后相同的异常可以在下次触发时再次提醒，不需要永久抑制。

### 5.3.2 关键词预警与定时扫描

关键词预警的处理逻辑相对简单。当检查报告保存后，业务层调用 WarningEngineServiceImpl.evaluateExamination 方法，传入患者信息、检查类型和报告结论文本。方法取出所有 ruleType 为 KEYWORD 的启用规则，将每条规则预设的关键词与报告结论字符串做不区分大小写的包含匹配，命中了就产出预警记录并推送。这个功能的设计灵感来自一个真实痛点——低年资医生在书写报告时，可能在结论中写入了"占位性病变"或"考虑肿瘤"这类带有严重病变倾向的措辞，但因为经验不足或者忙于接诊，没有主动向上级汇报，而系统可以自动捕获这些关键词并提醒科室管理层关注。

定时扫描的任务则集中在 WarningScannerTask 类中，由两个 @Scheduled 方法驱动。scanMissingData 每 30 分钟触发一次，逻辑是用 Patient 表遍历所有 isInvalid 为 false 的患者，对每位患者查一次其最近检验结果的 reportTime，如果距今已经超过规则中配置的 missingDays 天数阈值，就生成一条 MISSING 类型的预警；scanOperationAnomaly 每 15 分钟触发一次，逻辑是提取过去 5 分钟内全部操作日志记录，筛选出类型为"删除"或"作废"的记录，数其条数，如果超出规则中 thresholdHigh 设定的上限（默认 10 条），就判定为批量异常操作并预警，同时额外检查当前时间是否在非工作时段的范围内（22:00 至次日 06:00 以及周六周日），如果是且存在任何操作记录，也一并触发预警。

从图 5-23 可以看到，服务端使用了 JSR 356 标准的 @ServerEndpoint("/ws/warning/{userId}") 注解来声明 WebSocket 端点。前端在用户登录成功后立刻创建 WebSocket 连接，URL 中的 userId 取自 localStorage 中保存的登录用户 ID。服务端持有的是一个 ConcurrentHashMap<String, Session>，键是 userId，值是对应的 WebSocket Session。预警推送时，broadcast 方法遍历 Map 中所有 Entry，对每个 Session 调用 getBasicRemote().sendText 方法将 JSON 字符串发送到客户端。客户端的 onmessage 回调接收消息后，调用 Element UI 的 this.$notify 方法在屏幕右上角弹出预警通知框，同时更新顶部导航栏的预警徽标数字。

## 5.4 可视化统计与报表导出模块

### 5.4.1 统计图表

统计功能的实现分成两段：后端负责按维度做 GROUP BY 聚合，前端负责拿聚合数据渲染图表。后端核心在 StatisticsController 中，以 /statistics/countByTypes 接口为例，该接口接收四个参数：科室编码（deptCode）、开始日期（startDate）、结束日期（endDate）和时间粒度（period，取值为 day/week/month）。ServiceImpl 实现中根据 period 的值选择不同的 DATE_FORMAT 格式化字符串——日粒度用 '%Y-%m-%d'，周粒度用 '%Y-%u'，月粒度用 '%Y-%m'——然后对四张检查主表（ct_examination、mri_examination、enteroscopy_examination、pathology_examination）分别执行带 GROUP BY 的 COUNT 聚合，汇总成一个包含四种检查类型分项统计的 result 对象返回。

前端 StatisticsA.vue 组件在 mounted 生命周期里调用 echarts.init 绑定页面上预设的 div 容器，拿到后端数据后调 setOption 更新图表。柱状图的 xAxis.data 取的是部门名或医生名列表，series 里每种检查类型一条柱子，方便横向对比不同科室或医生的工作量。饼图则取所有检查类型的合计值，展示各自占总量的百分比。

## 5.5 数据导入与系统运维保障模块

### 5.5.1 Excel 批量导入

Excel 导入功能的设计核心在于"逐行处理、批量写库、大量数据不爆内存"。EasyExcel 官方提供的 AnalysisEventListener 继承模式天然支持这一目标——监听器的 invoke 方法被回调时，SAX 解析器只将当前这一行的数据注入内存，前一行已被处理过的数据已经被 GC 回收，因此在读取 1 行和读取 5 万行的真实内存占用几乎没有差别。导入过程中校验逻辑集中在 invoke 方法内部，每行被解析出来之后立即走一遍必填字段检查、日期格式验证、数值格式验证、项目代码字典对照和文件内去重五道关卡，任何一关不过就记录该行失败并跳过，而不会导致整个导入过程中断。

记录通过校验后先进入内存中的 List 缓冲区，缓冲区涨到 500 条时触发一次 MyBatis-Plus 的 saveBatch 批量写库，写完后 list.clear() 清空，让 GC 回收这 500 条对象的空间，然后 List 继续接收新数据。图 5-28 用活动图完整描绘了这个"读一行→验一行→暂存→满 500 写一批→清空继续"的循环。

  :HashMap查找文件内重复;
  :存入ImportContext.dataList;
}
partition "分批写入" {
  :遍历dataList;
  :数据库查重(编号+患者+时间);
  :通过者压入batchBuffer;
  if (buffer.size >= 500?) then (是)
    :saveBatch批量插入;
    :buffer.clear()释放内存;
  endif
  if (严格模式且有失败行?) then (是)
    :全部回滚;
    :返回失败结果;
  elseif (宽松模式) then (是)
    :跳过失败行继续;
  endif
}
:返回导入报告\n(总行数/成功数/失败数/失败明细);
stop
@enduml
```



图 5-28 中标出了这两种模式的行为差异：严格模式指只要有一行校验失败或数据库冲突，整个导入全部回滚，不产生任何脏数据，适合正式运行环境下的数据录入；宽松模式则会跳过所有失败行，只把校验通过的那些真正写进去，最后生成一份明细报告告诉用户哪些行失败了以及原因是什么，适合数据质量参差不齐的历史台账首次导入。

### 5.5.3 操作审计 AOP 设计

操作审计是跨越所有模块的横向功能，其实现借用了 Spring AOP 的环绕通知能力。定义上，@OperateLog 注解有三个属性——operationType（操作类型，如"新增""修改""删除""作废"）、operatedTable（操作的数据表名，如"patient""lab_result"）和 description（操作描述）。凡是需要被审计的 Controller 方法，标上这个注解即可，无需在方法体内额外写任何日志相关的代码。

图 5-33 用序列图完整描绘了 AOP 切面在环绕通知中的"拦截→抓取快照→放行→抓取快照→异步保存"五步操作。

```
@startuml 图5-33 AOP操作审计全流程序列图
actor 操作人
participant "目标Controller" as Ctrl
participant "OperateLogAspect" as AOP
participant "对应Mapper" as Mapper
database MySQL

操作人 -> Ctrl: 执行带有@OperateLog注解的业务方法
Ctrl -> AOP: @Around环绕通知拦截

AOP -> AOP: 提取注解中的operationType、operatedTable
AOP -> AOP: 从Request中提取userId、IP、当前时间

alt 操作类型为"修改"或"删除"或"作废"
  AOP -> Mapper: selectById(recordId)
  Mapper -> MySQL: SELECT ... WHERE id=?
  MySQL --> Mapper: 原数据行
  AOP -> AOP: 序列化为beforeContent JSON字符串
end

AOP -> Ctrl: joinPoint.proceed() 执行真实业务方法
Ctrl -> Mapper: 执行INSERT/UPDATE/DELETE操作

Mapper --> Ctrl: 返回

alt 操作类型为"新增"或"修改"
  AOP -> Mapper: selectById(recordId)

  MySQL --> Mapper: 操作后的数据行
  AOP -> AOP: 序列化为afterContent JSON字符串
end

AOP -> Mapper: @Async异步插入OperationLog

@enduml
```



从图 5-33 可以清楚地看到，审计日志的写入和业务返回之间没有因果关系——即使用了 @Async，日志保存是独立线程执行的，业务返回不等待它。这样设计的直接效果是，即使操作日志表所在的数据库节点临时不可用，主业务流程仍然能正常运行并返回成功，不会因为审计功能的异常拖垮整个系统。

日志防篡改的手段体现在 API 层面：OperationLogController 只提供了 GET /operationLog/list 和 POST /operationLog/page 两个查询接口，没有任何 UPDATE 或 DELETE 暴露。也就是说，从系统外部无法通过任何正常途径修改或删除已经写入的操作日志记录，唯一能留下痕迹的方式就是通过正常的业务操作新增一条新的日志记录，而这条新增操作本身也会再产生一条日志，形成永不断链的审计闭环。

### 5.5.4 RBAC 权限管控

权限管控的数据模型围绕四张表展开：sys_permission 存十六项细粒度权限（编码如 patient:view、ct:manage、warning:manage），sys_role 存四个预置角色（系统管理员、医生、检验技师、审计员），sys_role_permission 建立角色与权限的多对多映射，sys_user_role 建立用户与角色的多对多映射。

权限校验的工作发生在 JwtInterceptor 中。Token 校验成功后，取出当前用户的 userId，判断其角色：如果角色是 admin，直接 return true 跳过所有检查；否则，将当前请求的 URI 与预设的路径-权限编码映射表（一个静态 Map<String, String>，存储着 /patient → patient:view、/ctExamination → ct:view 等十五对映射关系）做匹配，取出该路径对应的权限编码，再调用 PermissionServiceImpl.hasPermission 查询该用户是否拥有此权限。PermissionServiceImpl 内部维护了一个 ConcurrentHashMap 作为本地线程安全的权限缓存，键是 userId，值是 List 权限编码集合，首次查询时从数据库加载后写入缓存，之后直接从缓存返回，权限变更时手动调用 clearCache 清除指定用户的缓存让其下次查询时重新加载。

```
@startuml 图5-35 RBAC权限校验序列图
actor 用户
participant "JwtInterceptor" as JWT
participant "PermissionServiceImpl" as PS
participant "PermissionMapper" as PM
database MySQL

用户 -> JWT: HTTP请求到达
JWT -> JWT: 验证JWT Token
JWT -> JWT: 提取userId和role
alt role = "admin"
  JWT -> JWT: 直接放行
else 其他角色
  JWT -> JWT: URI映射为权限编码\n如 /ctExamination → ct:view
  JWT -> PS: hasPermission(userId, "ct:view")
  PS -> PS: 查缓存 permissionCache.get(userId)
  alt 缓存命中
    PS --> JWT: true/false
  else 缓存未命中
    PS -> PM: selectPermissionCodesByUserId(userId)
    PM -> MySQL: SELECT DISTINCT p.code\nFROM sys_permission p\nJOIN sys_role_permission rp...\nJOIN sys_user_role ur...\nWHERE ur.user_id=?
    MySQL --> PM: ["patient:view","ct:view"...]
    PS -> PS: 写入缓存
    PS --> JWT: true/false
  end
  alt hasPermission = true
    JWT -> JWT: return true 放行
  else 权限不足
    JWT -> JWT: response.setStatus(403)
    JWT --> 用户: {"code":403,"msg":"权限不足"}
  end
end
@enduml
```



图 5-35 完整展示了权限校验的两种路径：admin 角色直接走快速通道，其他角色走 RBAC 验证通道。缓存的设计大幅降低了权限查询对数据库的访问频率——在科室 10 人并发的场景中，如果没有缓存，每次请求都需要执行一条三表 JOIN 的 SELECT 语句，平均耗时约 15 到 20 毫秒，而命中缓存后耗时降低到 0.1 毫秒以下，几乎不产生可感知的延迟。

### 5.5.5 数据库备份与恢复

备份功能由 BackupService 全权负责。全量备份时，backup 方法调用 Runtime.exec 启动系统后台进程执行 mysqldump 命令，通过 --single-transaction 选项保证 InnoDB 存储引擎下的事务一致性读，--routines 和 --triggers 确保存储过程和触发器同样被导出。导出的 SQL 文本通过 InputStream 读取到 byte[] 数组中，先经 GZIPOutputStream 压缩，再用 AES/GCM 模式加密（加密过程中使用每次生成的 12 字节随机 IV，密钥从 application.yml 配置中读取），最终写入 uploads/backups 目录下命名为"当前时间戳_enc_backup.bak.gz"的文件。增量备份的执行逻辑几乎相同，唯一的区别在于 mysqldump 命令中附加了 --where="create_time > '上次备份时间' OR update_time > '上次备份时间'" 参数，仅导出增量变化的数据行而非整张表。

加密算法选用 AES/GCM 而非更常见的 AES/CBC 的理由是，GCM 模式在加密的同时附带生成 128 位的认证标签，这个标签能用来验证密文在存储和传输过程中是否被篡改过，即便攻击者改了备份文件里 1 个字节，恢复时校验也会报错，避免因备份文件损坏或恶意篡改导致的数据库恢复异常。

```
@startuml 图5-37 备份恢复活动图
start
partition "全量备份 (凌晨2点)" {
  :@Scheduled触发fullBackup();
  :构建mysqldump命令\n(带--single-transaction等参数);
  :Runtime.exec执行系统命令;
  :读取stdout获得SQL文本;
  :GZIP压缩字节流;
  :AES/GCM加密(随机IV+认证标签);
  :SHA-256计算校验和;
  :写入backups目录;
}
partition "增量备份 (中午12点)" {
  :@Scheduled触发incrementalBackup();
  :查询上次备份时间;
  :mysqldump --where="create_time>上次时间";
  :执行压缩、加密、校验、写入;
}
partition "人工恢复" {
  :管理员在后台选中目标备份文件;
  :读文件→AES/GCM解密→GZIP解压;

  if (校验通过?) then (是)
    :通过mysql命令行还原SQL;
    :数据库恢复至备份时间点;
  else (否)
    :拒绝恢复，提示文件已损坏;
  endif
}

  :按修改时间对备份文件排序;
  :删除超出保留份数(30份)的旧文件;
}
stop
@enduml
```



图 5-37 完整描绘了备份→恢复→清理的闭环。恢复时双重的安全验证——先 AES/GCM 解密验证完整性，再 SHA-256 校验验证文件内容未被篡改——确保了从备份到还原的全链路数据安全性。
